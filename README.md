# blog-tanstack — deco.cx Blog Template

A production-ready blog template built with [TanStack Start](https://tanstack.com/start), [deco.cx](https://deco.cx) CMS, and Tailwind CSS v4. Supports server-side rendering, reading progress, search, categories, authors, and a magazine-style layout.

## Features

- **Magazine layout** — hero cover story, duo feature grid, and article feed on the home page
- **Full-text search** — server-side filtered search with highlighted matches
- **Categories & Authors** — filtered listing pages with paginated results
- **Reading progress bar** — visible on individual post pages
- **Hero scroll header** — transparent header transitions to white/blur on scroll over post cover images
- **Responsive** — mobile-first with a slide-out drawer menu
- **CMS-powered** — content is the Studio site `blog-tanstack`'s hosted release, read at runtime from the delivery CDN; `.deco/blocks/` holds the content this repository seeds it with

## Getting started

### Requirements

- [Bun](https://bun.sh) (recommended) or Node.js 24+

### Install and run

```sh
bun install
bun run dev        # predev runs `deco schema`
```

Open [http://localhost:5173](http://localhost:5173). Pages read the published release of the Studio site `blog-tanstack` from `delivery.decocms.com` (`src/cms.ts`); edit content in Studio and preview a draft with its `?__draft=` link.

### Build, check and test

```sh
bun run build      # prebuild runs `deco schema && deco check`, and on Workers Builds the release guard
bun run deco:check # deco schema --check && deco check (the saved blocks in .deco/blocks against the schema)
bun run typecheck
bun run test       # against the committed content, served by a fake delivery CDN (test/fake-delivery.ts)
```

## Project structure

```
.deco/
  index.ts             # the block map: every block type content can call, under its v7 names
  blocks/              # the content this repo seeds Studio with: pages, posts, categories, authors, site settings, CMS (never bundled)
  schema.gen.json      # generated by `deco schema` (committed)
src/
  cms.ts               # createCMS({ blocks, site }): the hosted release, read from the delivery CDN
  open-page.server.ts  # routes() + redirects() + matchRoute, one block promise per section (unknown URLs render /404 with a 404)
  page.functions.ts    # the server function the routes call
  routes/              # __root (layout, analytics), / and /$ (CMS pages), sitemap.xml
  views.tsx            # descriptor -> section component
  blocks.server.ts     # server-side props for sections (URL, site and blog settings, search index)
  seo/                 # the page `seo` blocks (post and topic SEO with their JSON-LD) and the head tags they produce
  sdk/blog/            # rendering shared by the sections: blocks.tsx (post block registry, default x custom),
                       # toc.ts, jsonLd.ts (schema.org for the listing pages), format.ts, scripts.ts
  components/blog/     # shared UI pieces (AuthorAvatar)
  utils/site-config.ts # site and blog settings -> SiteConfig (publisher, canonical origin)
  blog/, vendor/blog/  # blog loaders and the blog app's default post blocks (vendored from @decocms/apps-blog)
  sections/Blog/       # the blog UI sections, markup only
  sections/Blog/Post/  # this template's post blocks (site/sections/Blog/Post/*)
  edge/, worker-entry.ts  # createDecoWorker (drafts, redirects, Studio CSP, security headers; edge/worker.ts) and the page cache (edge/page-cache.ts)
```

## Blog settings

The blog's settings live in `.deco/blocks/deco-blog.json` (a `site/apps/deco/blog.ts` block, its v7 type): `pageSlug`,
`categorySlug`, `canonicalBaseUrl` (origin used for canonicals and JSON-LD),
`publisher` and `seo` (the title and description templates of the post and topic pages).

### Post content blocks

`post.sections` accepts two families of blocks, distinguished by `__resolveType`:

| Family  | Block map name     | v7 name (saved content)              | Rendered by                                                  |
| ------- | ------------------ | ------------------------------------ | ------------------------------------------------------------ |
| default | `post-default-*`   | `blog/sections/blocks/<Name>.tsx`    | the blog app's component (vendored in `src/vendor/blog/sections/blocks/`) |
| custom  | `post-*`           | `site/sections/Blog/Post/<Name>.tsx` | this template (`src/sections/Blog/Post/`)                    |

The mapping lives in `src/sdk/blog/blocks.tsx`. To add a custom block, create it in
`src/sections/Blog/Post/`, register it in `CUSTOM_BLOCKS`/`CUSTOM_TYPES` and add it to `.deco/index.ts`.

## Content management

Posts, categories and authors are saved blocks: one per document. Edit them in Studio. The site lists a collection from the release index (`client.entries(type)`) and reads each document once per revision (`src/vendor/blog/core/records.ts`); it never calls `client.list()`. The files in `.deco/blocks/` are what `deco push` sends to a draft.

### Adding posts

Create `.deco/blocks/collections%2Fblog%2Fposts%2Fyour-post.json`:

```json
{
  "name": "collections/blog/posts/your-post",
  "__resolveType": "blog/loaders/Blogpost.ts",
  "post": {
    "title": "Your Post Title",
    "slug": "your-post",
    "date": "2025-01-01",
    "excerpt": "Short description…",
    "image": "https://images.unsplash.com/photo-…?w=1280&h=720&fit=crop&q=80",
    "authors": [{ "name": "Author Name", "email": "author@example.com" }],
    "categories": [{ "name": "Engineering", "slug": "engineering" }],
    "sections": [
      { "__resolveType": "site/sections/Blog/Post/Heading.tsx", "level": "h2", "text": "First steps" },
      { "__resolveType": "site/sections/Blog/Post/Paragraph.tsx", "html": "<p>…</p>" }
    ]
  }
}
```

A post's `sections` are its body blocks: this template's `site/sections/Blog/Post/*` and the blog app's `blog/sections/blocks/*` sections of `.deco/index.ts`, saved under those v7 names.

Then run `npx deco check` and send it to a draft with `DECO_SITE=blog-tanstack npx deco push --draft=<name>` (`DECO_SITE` is deliberately not in `.env` or `wrangler.jsonc`, so `deco check` checks these files).

### Adding categories / authors

Follow the same pattern with `collections%2Fblog%2Fcategories%2F<slug>.json` (`blog/loaders/Category.ts`) and `collections%2Fblog%2Fauthors%2F<slug>.json` (`blog/loaders/Author.ts`).

## Notes on the v8 migration

- **Dependencies.** `@decocms/blocks` and `@decocms/tanstack` from npm, at the same version, pinned by the committed `bun.lock`. The v8 line has no `@decocms/start` or `@decocms/apps` counterpart: what those packages used to provide is either the binding's (`createDecoWorker`, `DecoPreview`, `createDecoRouter`, `decoServerFnFetch`, `decoTanstack`) or this site's code.
- **Hosted content, nothing bundled.** A request reads the index (`latest.json`, one read per isolate, re-checked every minute), the page `client.routes()` matched, the blocks it references, the config blocks named in code (`site`, `deco-blog`; `CMS` is inline in the index) and the blog collections the page shows. Bodies are content-addressed and kept per isolate, so a warm request makes no CDN request. `test/fetch-budget*.test.ts` and `test/sitemap.test.ts` pin the budget through the whole worker: a cold `/` makes 19 requests (the index, the page, `site`, `deco-blog` and the 15 posts), a cold post 24 (plus the 5 categories), `/sitemap.xml` 2 (the worker's redirect lookup prefetches the `/:slug` page it matches), a warm request 0.
- **Studio.** `DecoPreview` (in `src/components/RootLayout.tsx`) is the v8 Studio bridge; every section renders in a `<section data-manifest-key>` wrapper (`src/views.tsx`), header included, which Studio's editor selects. `createDecoWorker` lets Studio (production and staging) frame the site.
- **Blocks are awaited before the page renders** (`src/open-page.server.ts`), a deliberate exception to the TanStack Start guide, which keeps block promises unawaited. This site's blocks only read CMS content and settle together, and rendering them all in the first HTML chunk keeps the hero image's preload in the head, as on v7. `test/pages.test.ts` covers it. A block that starts fetching upstream should stop being awaited there.
- **Edge cache.** `src/edge/page-cache.ts` caches HTML pages and GET server functions (the page data of client-side navigations) in the Cloudflare Cache API, as v7's worker entry did, split by device and keyed by `<build>.<content revision>` (`cacheVersion`), so a deploy or a publish changes every key and nothing needs a purge. A page whose content failed to load (`x-deco-degraded`) is never stored; a stale copy stands in for it. HEAD answers GET's headers. `/deco/_liveness` answers `OK` (`createDecoWorker`).
- **Telemetry.** v7's `DECO_METRICS` Analytics Engine binding, the `DECO_OTEL_*` vars and the `CF_VERSION_METADATA` binding are gone. `createCMS` sends the CMS's metrics and every CMS error log (`errorSampleRate: 1`) to the hosted collector only when the `DECO_SITE_TOKEN` secret is set, as `blog-tanstack` (`DECO_SITE_NAME`), `production` (`DECO_ENV_NAME`) and the build's commit as `service.version` (`src/cms.ts`). The `deco-otel-tail` tail worker stays.
- **No visitor cookie.** `createDecoWorker` gives a first-time visitor a year-long `deco_segment` cookie for A/B tests; v7 sent none. `src/edge/worker.ts` drops it while the release saves no test and runs no campaign, so it comes back on its own once a test is saved in Studio.
- **Content.** `website/functions/requestToParam.ts` (v7's "the last path segment" function) was rewritten in content to the page's route `param` (`/:slug`, `/topics/:slug`, `/authors/:email`), a documented content migration that gives the same values. The v7 app blocks `site` and `deco-blog` keep their types (`site/apps/site.ts`, `site/apps/deco/blog.ts`) as settings blocks; `site` lost v7's app runtime fields (`routes`, `global`, `caching`, `firstByteThresholdMS`), which v8 doesn't read. v7 content no longer passes `deco check`, so publish only from these files.

## Deployment

Cloudflare Workers Builds deploys every commit on `main` as the worker `blog-tanstack`
(`https://blog-tanstack.deco-cx.workers.dev`). Content is the Studio site's hosted release, read at
runtime: a publish goes live without a deploy. (`https://blog-tanstack.deco.site`, the content's
`canonicalBaseUrl`, serves another site today.)

### First deploy on v8: publish, then merge

The v8 worker answers 500 on every page until the site has a release
(`https://delivery.decocms.com/sites/blog-tanstack/latest.json` answers 404 until then). In order:

1. `DECO_SITE=blog-tanstack DECO_TOKEN=<token> npx deco schema push`: Studio learns the block types.
2. `DECO_SITE=blog-tanstack npx deco push --draft=v8-seed`, from this branch's `.deco/blocks`. Never
   from v7 content (main's, or Studio's v7 copy): `deco push` doesn't run `deco check`, and v7
   content fails it (`website/functions/requestToParam.ts`, v7's app fields in `site`).
3. Check the draft (its `?__draft=` link), then `DECO_SITE=blog-tanstack npx deco publish --draft=v8-seed`.
4. Confirm `latest.json` answers 200, then merge.

The build refuses to deploy without a release: `prebuild` runs `scripts/require-release.mjs`, which
on Workers Builds (`WORKERS_CI`) fails unless `latest.json` answers, so a merge before the publish
keeps the live worker. That holds while the Workers Builds build command runs the `build` script
(`bun run build`). CI's "Website builds successfully" runs the same check (`REQUIRE_RELEASE=1`) and
requests `/`, so a pull request shows it too.

After that, content is edited in Studio. On every main commit `deco-schema-push.yml` pushes the
schema and checks the live release against the code (`deco check` with `DECO_SITE`).
